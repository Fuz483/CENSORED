# Пляцоўка

## Локальный запуск

Frontend: Node.js 22+, backend: Python 3.12+ и PostgreSQL.

1. Скопируйте `.env.example` в `.env`. Для локального PostgreSQL задайте
   `POSTGRES_HOST=localhost` и свои данные подключения. Для Docker оставьте `db`.
2. Для локального PostgreSQL подготовьте backend один раз (из корня):

   ```powershell
   python -m venv backend/.venv
   backend/.venv/Scripts/python.exe -m pip install -r backend/requirements.txt
   ```

   Затем каждый раз запускайте backend и frontend вместе из корня:

   ```powershell
   .\start-local.ps1
   ```

   Скрипт запускает PostgreSQL, применяет миграции, включает фоновый watchdog
   backend, проверяет готовность API, затем запускает frontend на
   `http://localhost:5173`. Watchdog следит за `/health` и автоматически
   перезапускает backend, если процесс завершился или API перестал отвечать;
   логи старта находятся в `.local/backend-supervisor.log` и
   `.local/backend-*.err.log`. Скрипт не запускает второй Vite, если frontend
   уже работает. Если API не готов, frontend не стартует.
   Для ручного запуска используйте команды API и frontend отдельно, но сначала
   дождитесь ответа `http://127.0.0.1:8000/health` со статусом 200.

   Альтернатива из корня: `docker compose up --build` (нужен Docker).
   Compose выполняет `scripts.seed`, который добавляет демонстрационные записи;
   не используйте это наполнение как реальный каталог.

3. Ручной запуск frontend (из `frontend/`, если не используется `start-local.ps1`):

   ```powershell
   npm install
   npm run dev
   ```

    Откройте `http://localhost:5173`. Vite использует `vite.config.ts`:
    прокси `/api` направлен на `127.0.0.1:8000` и занимает фиксированный порт,
    чтобы не запускаться незаметно на другом адресе.
   После изменения конфигурации перезапустите старые Vite-процессы.
   Не открывайте `index.html` напрямую — CSS требует сборки Tailwind.

Для удалённого backend скопируйте `frontend/.env.example` в `frontend/.env`.
`API_PROXY_TARGET` — адрес backend для разработки. `VITE_API_BASE_URL` — origin
backend для production-сборки (без `/api/v1`); при пустом значении настройте
reverse proxy `/api` на сервере размещения frontend.

## Что уже реализовано

- **Клиентский каталог:** поиск помещений по учреждению и типу, выбор даты на
  ближайшие семь дней, просмотр свободных интервалов и деталей помещения.
  Есть фильтры по городу и внутригородскому району. Справочник содержит
  115 городов Беларуси и Колодищи, которые уже были в списке школ.
  Расписание работает с 14:00 до 21:00 с шагом 15 минут; доступны спортзалы,
  актовые залы, кабинеты информатики, мастерские и бассейны.
- **Аккаунты:** регистрация арендатора с одноразовой капчей и вход арендатора/УО через backend,
  пароль хранится в виде хеша, авторизация — JWT. Сессия сохраняется в текущей
  вкладке. Арендатор может редактировать имя, телефон и электронную почту.
- **Бронирование:** арендатор читает демодоговор и подтверждает согласие.
  Сервер сохраняет текст, версию и время согласия вместе с заказом и выпускает QR.
  К оплате 0 BYN, данные карты не нужны. В личном кабинете доступны договор,
  QR-пропуск и отмена не позднее чем за два часа до начала.
- **Кабинет УО:** для демонстрационного учреждения можно добавить помещение с
  городом, районом, адресом, вместимостью, тарифом, расписанием и фотографией. Данные сохраняются
  на сервере. Кабинет показывает помещения и заявки арендаторов учреждения.
- **Постоянные клиенты:** школа указывает группу, помещение, дату первого занятия
  и интервал. Резерв повторяется каждую неделю в это время до отмены серии.
  Если время уже занято разовой бронью или другой серией, сервер отклоняет
  создание. Резерв скрывает занятые интервалы в каталоге и не выпускает QR.
- **Пост охраны:** отдельная страница `/guard` сканирует QR камерой и показывает
  решение сервера о допуске, проверяя статус и дату брони.
- **Дополнительно:** интерфейс на русском и белорусском языках; справочник
  учреждений; API расчёта распределения стоимости по Указу № 150.

## API и ограничения

- Регистрация/вход: `GET /api/v1/auth/captcha`, `POST /api/v1/auth/register`,
  `/auth/login`; восстановление
  сессии: `GET /api/v1/auth/me`. JWT хранится в `sessionStorage` текущей вкладки.
  Капча действует три минуты и расходуется после первой попытки. Задания хранятся
  в памяти процесса, поэтому для этой демоверсии запускайте один воркер API.
- Доступность: `GET /api/v1/rooms/available?date=YYYY-MM-DD&type_room=sport_hall`.
  Frontend загружает все типы помещений на неделю одним запросом
  `GET /api/v1/rooms/catalog?start=YYYY-MM-DD&days=7`.
- Бронь: `POST /api/v1/bookings/agreement` возвращает текст и токен договора.
  `POST /api/v1/bookings` требует Bearer JWT, токен и `agreement_accepted: true`.
  Минимум 1 час, шаг 15 минут.
  История: `GET /api/v1/bookings/user/{user_id}`. Отмена: `PATCH
  /api/v1/bookings/{id}/state` с `{"state":"cancelled"}`.
- После согласия с договором новые брони получают статус `confirmed` и QR-код.
  Несколько броней отправляются отдельными POST. При частичном успехе
  проверьте историю, прежде чем повторять запрос. Охрана проверяет код, статус и
  дату брони: допуск разрешён только в день бронирования.
- Данные хранятся в трёх таблицах PostgreSQL: `users`, `orders` и `listings`.
  В `orders` входят разовые заказы и еженедельные резервы. В `listings`
  хранятся объявления школ и ссылки на фотографии. Миграция `0008_orders_and_listings`
  переносит существующие данные и сохраняет старые QR. Файлы фотографий
  хранятся на сервере. У части демообъявлений нет подтверждённых адресов.
- Подключён API расчёта распределения стоимости, но он не участвует в оформлении
  брони. Бронирование сейчас бесплатное и сразу подтверждается.

## Кабинет УО для хакатона

В форме входа выберите «УО»: один пароль открывает кабинет «Лицей БГУ».
Для локальной демонстрации включён `UO_DEMO_ENABLED=true` в `.env`.
По умолчанию в `.env.example` режим выключен. Аккаунт хранится в PostgreSQL,
пароль — только в виде хеша; проверка выполняется на backend, сессия — JWT.
Из `backend/` можно задать или заменить пароль:

```powershell
.venv/Scripts/python.exe -m scripts.setup_uo_demo
```

Кабинет показывает три демонстрационных помещения, свободные часы и заявки
арендаторов Лицея БГУ. Во вкладке «Постоянные клиенты» можно создать или отменить
еженедельный резерв. Кнопка «Обновить данные» загружает свежие данные.
Помещения и расписание предназначены для демонстрации и не
подтверждены учреждением. Выдача паролей главным администратором, несколько
учреждений, ограничение попыток входа и смена/отзыв паролей — отдельный этап
перед production. Демонстрационный режим не следует включать на публичном
production-сервере.

## Что ещё нужно реализовать

### Приоритетно перед реальным запуском

1. **Полноценный каталог помещений:** реализовать API редактирования и архивирования
   объявлений с правилами доступа владельца. Подтвердить адреса,
   фотографии, вместимость, тарифы и расписания у учреждений.
2. **Управление для УО:** подключить редактирование/удаление помещений и ручное
   создание броней; добавить управление несколькими учреждениями и безопасную
   выдачу, смену и отзыв учётных данных УО.
3. **Оплата:** выбрать и подключить платёжного провайдера, обрабатывать
   подтверждение/ошибку/возврат платежа и только после подтверждения менять
   статус брони. Сейчас брони создаются бесплатными и подтверждёнными.
4. **Безопасность аккаунтов:** реализовать подтверждение телефона или почты,
   восстановление пароля, ограничение частоты входа, отзыв сессий и безопасную
   production-конфигурацию секретов. Не публиковать демонстрационный режим УО.

### После базового запуска

5. **Данные и процессы:** определить правила отмены и возвратов, уведомления
   арендатора и УО о брони/изменениях, а также аудит действий и администрирование
   каталога.
6. **Проверки и эксплуатация:** добавить frontend-компонентные и end-to-end
   тесты, проверить параллельное бронирование и сценарии оплаты; настроить
   production-развёртывание, резервное копирование, мониторинг и журналирование.
7. **Расширение географии:** подключать учреждения за пределами демонстрационного
   каталога только после подтверждения владельца, адреса, расписания и условий
   аренды.

## Проверки

Frontend: `npm run build` из `frontend/`.

API-тесты из `backend/` (изолированная SQLite БД, не затрагивают PostgreSQL):

```powershell
.venv/Scripts/python.exe -m pip install -r requirements-dev.txt
.venv/Scripts/python.exe -m unittest discover -s tests -v
```
